# Patterns UI & pièges React/CSS récurrents

## Design tokens

Toujours utiliser les tokens de `src/lib/theme.ts` (`palette`, `ink(alpha)`, `withAlpha(hex, alpha)`, `inkOn(hex)`, `radius`, `shadow`) pour les couleurs de marque dans un `style={{}}` — jamais de hex/rgba en dur. Dans un `className` Tailwind, référencer directement la variable CSS (`bg-[var(--surface-raised)]`) plutôt qu'un nom de couleur Tailwind générique (`bg-white`, `bg-gray-50`…) : la palette n'a **jamais** de blanc pur ni de gris neutre (« never white, never dark », doctrine du design system). `theme.ts` doit rester synchronisé avec les variables CSS portées par le Culture Design System dans `globals.css` (bloc `@theme inline` pour les classes Tailwind nommées type `bg-cream`/`text-ink`/`text-amber`, et le bloc `:root` pour les `var(--x)` bruts) — les deux exposent les mêmes valeurs sous deux syntaxes différentes.

**Couleur choisie par l'utilisateur en fond d'un élément** (libellé d'examen, teinte catégorielle) : le texte posé dessus passe par `inkOn(hex)` — luminance perçue au-dessus du seuil → `palette.ink`, en dessous → `palette.onInk`. Jamais une couleur d'encre fixe sur un aplat dont on ne maîtrise pas la valeur.

**Couleur sans token exact.** Le Culture Design System n'a que 6 familles (vert/tan/ink/danger/gold/surfaces) — une couleur héritée de l'ancienne charte ou de la maquette qui ne correspond à aucune n'a pas d'équivalent direct. Chercher la valeur la plus proche par distance colorimétrique parmi les tokens documentés (`docs/design/_ds/culture-design-system-…/tokens/colors.css`) plutôt que garder le hex en dur ; si le rôle sémantique manque encore à `palette`, l'y ajouter (ex. `tanStrong`/`greenTint`/`tanTint`/`goldTint`, ajoutés au fil du chantier de refonte UI pour des rôles présents dans les tokens du design system mais pas encore dans `palette`). Pour une **teinte catégorielle** hors palette de marque (distinguer visuellement plusieurs catégories — types de question, pastilles de membre, libellés d'examen — sans réutiliser indéfiniment le vert ou l'ambre), voir les précédents `avatarTones` et `categoryTones` : un petit tableau nommé et documenté dans `theme.ts`, jamais du hex dispersé dans les composants.

Icônes : exclusivement `lucide-react`, jamais de symbole Unicode/emoji en guise d'icône fonctionnelle quand un composant Lucide équivalent existe (`Check`, `X`, `PenLine`, `Flag`…) — règle absolue, voir `CLAUDE.md` §1.

## Layout plein écran sous `[locale]/layout.tsx`

Le layout empile un header (hauteur réelle 65px = `h-16` + `border-b` 1px) puis `<main className="flex-1">`. **Ne jamais utiliser `100vh`/`min-h-screen` brut** sur le conteneur racine d'une page — utiliser `calc(100vh - 65px)`, sinon on ajoute systématiquement 65px de trop par rapport à la fenêtre.

**Le `DashboardHeader` (espace connecté) est collant** (`sticky top-0 z-50`, 60px + 1px de bordure) : il reste dans le flux, donc aucune page n'a de compensation de hauteur à faire, **mais tout autre bloc `sticky` d'une page desktop doit décaler son `top` de 60px** sous peine de se coller sous la barre (précédents : barre latérale des paramètres d'atelier `top: 84`, colonne d'identité de la page création `lg:top-[76px]`). Le z-index de 50 passe au-dessus des sous-barres collantes des pages (z-40) et reste sous les modales, qui sont plus bas dans le DOM.

**Contexte de navigation persistant sans requête bloquante.** La barre du haut est identique sur toutes les pages où elle est affichée — sélecteur d'atelier et groupe d'onglets compris. Hors page d'atelier (jardin, profil, tableau de bord), l'URL ne porte aucun atelier : le header a donc besoin du dernier atelier visité. Le lire en base depuis le layout ajouterait une requête bloquante au rendu de *toutes* les pages ; le lire depuis `localStorage` n'agit qu'après hydratation, donc le bloc « pope » quand même. Le pattern retenu est un **cookie écrit par le client et lu par le layout** (`src/lib/lastWorkshopCache.ts`) : présent dans le HTML initial, coût nul, et une server action le rafraîchit en arrière-plan. Le `userId` est stocké dans le cookie et vérifié à la lecture (poste partagé). À réutiliser pour tout contexte de navigation de ce genre.

## Pattern « modifications non enregistrées »

Pour les pages de formulaire sans bouton « enregistrer » permanent : un état `formValues` (objet unique regroupant tous les champs éditables) comparé à un `savedSnapshot` (`useState(formValues)` initial) via `JSON.stringify` pour calculer `isDirty`. Si `isDirty`, une barre flottante « enregistrer » apparaît, et un listener global (`document.addEventListener('click', ..., true)`, capture phase) intercepte tout clic sur un `<a>` interne pour ouvrir une modale de confirmation (sauf clic modifié/molette/`target="_blank"`/ancre `#`) plutôt que de naviguer directement. Un handler `beforeunload` (avec un ref pour éviter les closures obsolètes) couvre la fermeture d'onglet/rechargement. Limite connue : la navigation `popstate` (bouton retour du navigateur) n'est pas interceptée. Pour ajouter un champ à un formulaire existant qui utilise ce pattern : ajouter sa clé dans `formValues` (donc dans `savedSnapshot`) et l'inclure dans l'appel de sauvegarde — `isDirty` et la barre suivent automatiquement.

Référence : `src/app/[locale]/workshops/[id]/settings/SettingsClient.tsx`.

## Modale de confirmation (pattern à réutiliser)

Carte crème `borderRadius: 20`, icône d'avertissement, titre/description centrés, actions en bas (« Confirmer » / « Annuler », ou 3 actions type « Enregistrer et quitter » / « Annuler » / « Quitter sans enregistrer »). À utiliser pour toute action destructive ou décision à conséquence (suppression, navigation avec perte de données).

## Borner un texte qui pourrait déborder : en largeur, pas en caractères

Un plafond du type `name.slice(0, 30)` compte des caractères là où le débordement se mesure en pixels : il coupe des noms qui avaient la place de tenir, et laisse passer les caractères larges (majuscules, « m ») qui débordent quand même. Poser la borne sur l'élément : `maxWidth: '100%'` (+ `boxSizing: 'border-box'`) sur le bloc, et `minWidth: 0` + `overflow: hidden` + `textOverflow: 'ellipsis'` + `whiteSpace: 'nowrap'` sur le texte lui-même. **`minWidth: 0` est indispensable** dès que le texte est un élément de flex : sans lui, un élément de flex refuse de se réduire sous la largeur de son contenu et le « … » ne se déclenche jamais. Les cibles de clic voisines (boutons, pictogrammes) gardent leur `flexShrink: 0` — c'est le texte qui cède, pas elles.

**L'infobulle de secours ne se déduit alors plus du texte** : la coupe se décide au rendu. La mesurer (`scrollWidth > clientWidth + 1`, la tolérance d'un pixel écartant les arrondis sous-pixel) dans un `useLayoutEffect` + `ResizeObserver` sur l'élément de texte, gardée par une comparaison explicite (voir plus bas). Sans cette mesure, il ne reste que deux mauvaises options : une infobulle sur tout, y compris ce qui se lit déjà en entier, ou aucune sur ce qui est coupé. Référence : `LabelPill` (`examen/examShared.tsx`, 18/08/2026).

## Fermeture des panneaux au clic extérieur — `useDismissOnOutsideClick`

Point d'entrée unique pour tout panneau flottant qui se ferme quand on clique ailleurs (`examen/examShared.tsx`). Deux règles indissociables, décidées le 12/08/2026 :

- **Le clic qui ferme ne fait que ça.** Il n'atteint pas ce qu'il y avait dessous — ni le bouton visé, ni le focus, ni la sélection. Un panneau ouvert capture le premier clic ; il en faut un second pour agir. Sans ça, quitter un panneau déclenchait au passage l'action de l'élément survolé.
- **Toutes les couches se ferment dans le même geste.** Chaque panneau juge de son propre côté avec sa `ref`. Ne jamais faire qu'une couche se mette en retrait tant qu'une autre est ouverte (« si le libellé est en édition, le panneau de filtres ne se ferme pas ») : il faut alors autant de clics que de couches.

Mise en œuvre : écoute `mousedown` **en capture sur `document`** — elle passe avant React (qui pose ses écouteurs sur la racine de l'app, plus bas), et `stopPropagation` n'empêche pas les autres couches de se prononcer (les écouteurs d'un même nœud s'exécutent tous, seule la descente est coupée). Le `click` est un événement distinct du `mousedown` : il faut l'avaler à part, avec un écouteur d'un coup retiré sur le clic avalé et, à défaut, au tour de boucle suivant le `mouseup` (un `mousedown` ne produit pas toujours un `click`).

**Le défilement ferme aussi**, mais seulement celui d'un conteneur qui *porte* le panneau (`target.contains(panelRef.current)`). C'est la raison même de le fermer : posé en `position: fixed` pour échapper au rognage de sa colonne, il suit son bouton et finit par passer par-dessus la barre de navigation. Défiler une colonne voisine ne le déplace pas, et n'a donc pas à le fermer ; le test écarte du même coup le défilement de la liste *interne* du panneau. Écoute en capture (`scroll` ne remonte pas).

Les modales sont hors du jeu, au clic comme au défilement : `Modal` marque sa racine d'un `data-modal-layer`, que le hook ignore. Elles se posent au-dessus des panneaux et gèrent leur propre sortie ; sans ce repère, un bouton de confirmation rendu dans un portail (donc hors de l'arbre du panneau) passerait pour un clic ailleurs et serait avalé avant d'être reçu.

## Pièges React/CSS rencontrés

- **`setState(prev => ...)` n'est pas synchrone.** Construire l'objet à passer à une server action **avant** l'appel à `setXxx`, jamais à l'intérieur de l'updater avec une variable externe capturée (`let saved = null; setXxx(prev => { saved = ...; return ... })` — `saved` reste `null` après l'appel). De même, **n'appelle jamais une server action à l'intérieur d'un updater `setState`** (l'updater s'exécute pendant la phase de rendu ; une server action qui fait `revalidatePath`/`router.refresh()` déclenche « Cannot update a component while rendering a different component »). Collecter le résultat dans une variable externe pendant l'updater, puis appeler la server action après `setXxx`.

- **`useLayoutEffect` pour mesurer une hauteur réelle (`ref` + `getBoundingClientRect`) :** ne pas mettre de tableau de dépendances vide si le contenu peut changer (réordonnancement, ajout) — la mesure doit re-tourner à chaque rendu. Pour éviter la boucle infinie de `setState`, garder la mise à jour derrière une comparaison explicite (`if (changed) setHeights(...)`).

- **Dans un bloc dont la hauteur est mesurée, l'air se met en `padding`, jamais en `margin`.** `offsetHeight` exclut les marges, et deux marges verticales voisines fusionnent : un bloc mesuré qui espace son contenu par une marge est systématiquement plus court que la place qu'il occupe. Tout ce qui consomme la mesure décroche alors — et le décalage s'accumule ligne après ligne. Précédents, tous sur la feuille A4 de l'onglet examen : l'écart de 40px d'une question liée, puis (12/08/2026) la bande de saut de page et la cale « partie vide », qui faisaient perdre 20px à la pagination et désalignaient la gouttière de tout ce qui suivait un saut de page. Si l'élément visible doit garder son propre cadre (bordure, fond), l'envelopper dans un bloc porteur du `ref` et du `padding` plutôt que déplacer le cadre.

- **Un composant à état ne doit jamais dépendre de sa propre hauteur pour savoir où il est monté.** Si sa position dans l'arbre React (page, colonne, groupe) est calculée à partir de sa hauteur mesurée, le moindre champ qui s'ouvre le fait changer de parent : React le démonte et le remonte, et tout son `useState` repart de zéro — panneau replié, saisie en cours perdue. Précédent : le formulaire en ligne de la feuille d'examen, dont la pagination A4 décidait la page à partir de sa hauteur (12/08/2026) — il se remontait dès l'ouverture, et un bouton de barème qui masque un champ suffisait à refermer ses paramètres avancés. Correctif : sortir le bloc en édition de la décision de saut de page (`PageBlock.neverStartsPage`), sa page s'étirant de toute façon pour le porter. Pour diagnostiquer ce genre de cas, compter les montages (`useEffect(() => { …compteur… }, [])`) — en dev, StrictMode double le compte, un montage réel vaut 2.

- **Aligner une colonne parallèle sur une ligne de texte : mesurer, pas recalculer.** Deux colonnes voisines qui doivent se répondre ligne à ligne (gouttière d'actions ↔ contenu) ne peuvent pas déduire le retrait haut d'une ligne d'une constante : un média (image, note audio) au-dessus de l'énoncé le décale d'une hauteur inconnue avant chargement. Mesurer l'écart réel et le repasser en `paddingTop` à la colonne d'en face. Dans une zone en `zoom`, ramener l'écart en unités locales en calibrant sur la ligne elle-même (`rect.height / offsetHeight`) plutôt qu'en lisant la variable CSS d'échelle.

- **`position: fixed` à l'intérieur d'un ancêtre avec `transform: scale(...)` (ou tout autre `transform`) combiné à `overflow: auto`** : le `fixed` cesse d'être positionné par rapport au viewport et devient un élément scrollable avec son contenu. Toute modale/toast ajoutée dans une zone mise à l'échelle (ex. panneaux avec zoom) doit passer par `createPortal(..., document.body)`.

- **Mettre à l'échelle un bloc de largeur fixe selon la place disponible : `zoom`, pas `transform: scale()`.** Précédent : la feuille A4 de l'onglet examen, de 75 % à 140 % par paliers (`--exam-scale`, `.exam-shell` dans `globals.css`). `zoom` agit sur la mise en page — le conteneur occupe exactement la place du contenu mis à l'échelle, sans compensation de hauteur ni marges négatives — et la largeur disponible des enfants est divisée par le facteur, donc un bloc de largeur fixe continue de tomber pile dans son panneau à toutes les échelles (les marges du panneau doivent alors s'exprimer en `calc(… * var(--echelle))` pour rester proportionnelles). Contrairement à `transform`, il ne casse pas les descendants en `position: fixed` (un `inset: 0` couvre toujours la fenêtre entière — vérifié). Côté mesures : **`offsetHeight`/`clientHeight` restent en unités locales (non zoomées), `getBoundingClientRect()` est dans le repère de la fenêtre** — ne jamais mélanger les deux dans un même calcul (une pagination mesurée en `offsetHeight` reste juste à toute échelle ; un centrage de défilement comparé à un `clientHeight` de conteneur non zoomé doit lire la hauteur sur le rectangle). Garder le conteneur défilant **hors** du zoom : ses `scrollTop`/`scrollTo` restent ainsi dans le même repère que les rectangles. Enfin, les paliers se choisissent en CSS pur (media queries sur des variables) plutôt qu'au `ResizeObserver` : pas d'état, pas de saut après hydratation.

- **`ResizeObserver` sur un conteneur de mise en page avec `overflow` conditionnel** : ne pas mettre `overflow: auto` par défaut si l'overflow n'est nécessaire que dans un cas particulier — l'apparition/disparition d'une scrollbar redéclenche l'observer et peut casser une animation ou fausser une mesure en cours. Basculer `overflow` seulement dans le mode qui en a besoin. Un `ResizeObserver` doit rester connecté en continu (ne pas le déconnecter après la première mesure), sinon la mise en page se fige au zoom navigateur suivant.

- **Centrer un conteneur potentiellement plus large que son parent, en le gardant scrollable** : ne jamais `justifyContent`/`alignItems: 'center'` sur un flex/grid scrollable — si le contenu dépasse, les navigateurs refusent un `scrollLeft` négatif, donc la partie qui dépasse à gauche devient inatteignable au scroll. Utiliser `width: 'fit-content', margin: '0 auto'` : en cas de dépassement, la marge se résout à 0 (alignement à gauche, immédiatement visible) et le reste est atteignable en scrollant.

- **Rangée flex dont un panneau n'a que des enfants `position: absolute`** (ex. le panneau « pots » de `ProgrammeTab`) : ce panneau a une hauteur intrinsèque nulle — sa hauteur visible vient soit d'un frère avec du contenu réel, soit d'une hauteur définie. Si l'ancêtre est en `minHeight` (hauteur `auto`), un `height: '100%'` ne résout pas ; supprimer le frère qui donnait la hauteur fait s'effondrer toute la rangée à 0 px → « page blanche » inexpliquée. Toujours poser un `minHeight` explicite sur le conteneur de la rangée dans ce cas.

- **Deux systèmes d'avatar distincts existent** — ne pas les confondre : le composeur PNG actuel (`src/components/avatar/avatarConfig.ts`, rendu par `AvatarComposer`, édité via `/profile/avatar`, source de vérité `publicMetadata.avatarParts` sur le compte Clerk) et un système SVG legacy (`src/components/avatar/types.ts`, rendu par `AvatarSVG`, utilisé uniquement par la `Navbar` visiteur — invisible une fois connecté). Toujours vérifier de quel fichier `avatarConfig`/`types` on importe avant de modifier le rendu d'avatar.
